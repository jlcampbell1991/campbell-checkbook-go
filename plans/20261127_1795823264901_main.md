# Implementation Specification: main

## 1. Objective
Create a minimal Go entry‑point that prints the string "hello world" to standard output. The new program should coexist with the existing `main.go` (which starts the Checkbook web service) without interfering with it.

## 2. Existing Architecture and Relevant Code
- The repository root already contains a `main.go` that bootstraps a full HTTP server using **chi**, templates, DB migrations, etc. This file is the entry point for the Checkbook application.
- All source code lives under `cmd/handlers`, `internal/`, `static/`, and `views/`.
- The project follows the Go conventions defined in `~/.config/opencode/go-conventions.md` (run `gofmt`, `go vet`, `go test`).
- The `Makefile` provides a `run` target that builds and executes the root `main.go`.

## 3. Required Changes
### 3.1 Files to Modify
- **None.** No existing file needs to be altered for this task.

### 3.2 Files to Create
- **Path:** `cmd/hello/main.go`
  - **Responsibility:** Provide a tiny, self‑contained program that prints `hello world` when executed.
  - **Content Overview:**
    ```go
    package main

    import "fmt"

    func main() {
        fmt.Println("hello world")
    }
    ```
  - **Integration:** This file lives in its own `cmd/hello` package, so building it will not affect the existing application. It can be compiled with `go build ./cmd/hello` or run directly with `go run ./cmd/hello`.

## 4. Implementation Plan
1. **Create directory** `cmd/hello` if it does not exist.
2. **Create file** `cmd/hello/main.go` with the exact code shown above.
3. Ensure the file uses the standard `package main` and imports only `fmt`.
4. Run `gofmt -s -w .` to format the new file.
5. Run `go vet ./...` to confirm no vet issues.
6. Execute `go run ./cmd/hello` locally to verify the output is exactly `hello world` followed by a newline.

## 5. Code Samples and Technical Details
```go
package main

import "fmt"

func main() {
    fmt.Println("hello world")
}
```
- The program uses `fmt.Println` to automatically append a newline, matching typical console output expectations.
- No command‑line flags, environment variables, or external dependencies are required.
- The file resides in its own module path (`cmd/hello`) to avoid naming collisions with the existing `main.go`.

## 6. Error Handling and Edge Cases
- There are no runtime error conditions for this program; `fmt.Println` never returns an error.
- The only edge case is ensuring the string is exactly `hello world` (lower‑case, single space) with no trailing spaces.

## 7. Testing Requirements
- **Unit Test (optional):** Create `cmd/hello/main_test.go` that captures `stdout` and asserts the output equals `hello world\n`. This is not strictly required but provides confidence.
- No changes to existing test suites are needed.
- Ensure the new test (if added) passes with `go test ./...`.

## 8. Acceptance Criteria
- [ ] A new directory `cmd/hello` exists.
- [ ] File `cmd/hello/main.go` contains a `main` function that prints exactly `hello world`.
- [ ] The program builds and runs without errors (`go run ./cmd/hello`).
- [ ] Output verification: running the program prints `hello world` followed by a newline and nothing else.
- [ ] `gofmt -s -w .` reports no formatting changes needed.
- [ ] `go vet ./...` reports no issues.
- [ ] (If test added) `go test ./...` passes.

- **Question:** Should a unit test be added for this tiny program? It is not required by the task description, but adding one could improve test coverage.
- **Assumption:** The user intends the new program to be separate from the existing web service, hence the placement under `cmd/hello`.
- **Assumption:** No modifications to the existing `main.go` are desired; the request is to *add* a simple entry point, not replace the existing one.
